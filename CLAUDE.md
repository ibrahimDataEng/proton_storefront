### Account Confirmation & password-reset redirects

`/reset-password` and `/confirm-account` both work correctly — `redirectUrl` in `RegisterForm.tsx`/`ForgotPasswordForm.tsx` is built via `useLocale()` + `useParams()` as `${origin}/${locale}/${channel}/...`. **Do not copy the older bare `${origin}/reset-password` pattern from memory** — see saleor-payments skill's redirect-URL bug pattern for why. `confirmAccount` (not `accountConfirm`) is the real mutation — `src/graphql/mutations/AccountConfirm.graphql`, route at `src/app/api/auth/confirm-account/route.ts` (raw fetch, mirrors `set-password/route.ts`), page + `ConfirmAccountClient.tsx`.

### Mandatory Phone Number — Registration + Login-Gate (proton_identity)

Phone is required at registration but **never blocks account creation** — `accountRegister` has no phone field at all (confirmed via schema introspection), so the phone write is always a separate, post-login call to the external `proton_identity` service (see that repo + `saleor_platform/README.md`'s proton*identity section for the service itself). `PHONE_IDENTITY_SERVICE_URL`/`PHONE_IDENTITY_SERVICE_TOKEN` — server-side only, never `NEXT_PUBLIC*` (the token authorizes reading/writing every account's phone number).

- **`src/lib/identity.ts`** — shared server-side helper: `resolveAuthenticatedUser()` (reads the caller's own access-token cookie, fetches `me { id }` — never trusts a client-supplied userId, same discipline as `account/actions.ts`) and `callIdentityService()` (proxies to proton_identity with the service Bearer token + a hard `AbortSignal.timeout(3000)` so a hung proton_identity can never stall a request indefinitely).
- **`POST /api/identity/set-phone`** — forwards to proton_identity's `POST /phones`, maps its response to `{ outcome: "success" | "invalid" | "conflict" | "service_error" }`. Used by both RegisterForm's post-auto-login write and PhoneGate's own submit.
- **`GET /api/identity/phone-status`** — **FAIL-OPEN BY DESIGN, do not "fix" this to fail-closed.** If proton_identity is unreachable, times out, or returns a non-200/malformed body, this route returns `{ hasPhone: true }` (i.e. "don't gate") — logging the failure server-side, but never blocking a user from their own account over a proton_identity outage. Only a genuine, successfully-received `hasPhone: false` triggers the gate. Verified live: stopping proton_identity entirely does not lock out an existing user with a phone already on file — confirmed via the request actually round-tripping the full 3s timeout before failing open, not merely skipping the check.
- **`PhoneField.tsx`** (`src/ui/components/auth/`) — shared country-code-select + number-input component, extracted from `SupplierApplicationForm.tsx`'s inline pattern (same regex validation, same `PHONE_CODES`, no validation library). Used by both `RegisterForm.tsx` and `PhoneGate.tsx`. i18n namespace `phoneField`.
- **`PhoneGate.tsx`** — the login-gate: on any fresh login (effect keyed on `user.id`), calls `phone-status`; if `hasPhone:false`, renders a non-dismissible modal-style overlay (no Escape, no backdrop-click, modeled on `AuthModal.tsx` minus the dismiss affordances) blocking until the phone is saved or the user signs out. **Escape hatch**: after 2 consecutive _service_-error (not 400/409) submit failures, a "Continue for now" option appears — a proton_identity outage must not be a permanent dead-end. i18n namespace `phoneGate`.
- **Registration flow, precisely**: this environment has `enableAccountConfirmationByEmail` **on** by default — the confirmation-disabled (auto-login) path exists in code and was verified separately (by temporarily toggling the Saleor site setting in a Django shell, not a code path — reverted after) but is not the default locally. On the confirmation-_disabled_ path, `RegisterForm.tsx` fire-and-forgets the phone write immediately after auto-login. On the confirmation-_required_ path (the default here), no token exists yet at registration time, so nothing can be written — `pendingPhone.ts` (localStorage, keyed by email, 7-day TTL) best-effort carries the value forward for the **same device**; `LoginForm.tsx` silently attempts to flush it on the next successful login. Cross-device confirmation (e.g. registered on desktop, confirmed via a phone's email app) has no pending entry — PhoneGate is what catches that case, and does so unconditionally, regardless of device. Both recovery paths were verified live: same-device resolves silently with no gate ever shown (self-healing); cross-device (or an expired/cleared pending entry) correctly triggers the gate.
- **Known gotcha, confirmed by testing, not a hypothetical**: the post-registration failure notice (`PhoneSaveNoticeBanner.tsx`) does **NOT** use AuthContext state. An earlier version did, and it silently never appeared — `router.refresh()` (called right after `router.push("/")` in both RegisterForm and LoginForm) remounts `AuthProvider`, which orphans any closure holding a setter captured before that remount (confirmed: `pendingPhone` was correctly saved by the failure branch, proving the code ran, but the context flag update landed on the discarded pre-refresh instance and was lost). Fixed by decoupling the notice from React component identity entirely — `src/lib/auth/phoneSaveNotice.ts` dispatches a plain `window` event (`notifyPhoneSaveFailed()`), and `PhoneSaveNoticeBanner.tsx` listens via `window.addEventListener` in a mount-only effect. **If a future session is tempted to route more post-navigation async feedback through AuthContext, re-read this note first** — the same remount will silently eat it.

### Phone OTP Login (proton_auth_plugin)

Second login path alongside email/password, using the same phone/OTP infrastructure `proton_identity` already exposes. `LoginForm.tsx` gained an Email/Phone tab (mirroring `AuthFormWrapper`'s own tablist pattern) — used identically in both `AuthModal` and the standalone `/login` page since both render `LoginForm`. Phone mode is 2 steps: enter phone → `POST /api/otp/send`, then enter the 6-digit code → `POST /api/auth/phone-login`.

- **`POST /api/otp/send`** — thin proxy to proton_identity's `POST /otp/send` via `identity.ts`'s existing `callIdentityService` (reused, not duplicated — same SERVICE_TOKEN header, same 3s timeout). Maps outcomes to `{ outcome: "sent" | "invalid_phone" | "rate_limited" | "service_error" }`.
- **`POST /api/auth/phone-login`** — calls Saleor's `externalObtainAccessTokens(pluginId: "com.tawasiplus.phone-auth", input: JSON)` **directly** (public mutation, same trust tier as `tokenCreate` — no SERVICE_TOKEN involved; the real verification-against-proton_identity happens server-to-server inside the Saleor plugin itself, not in this route). On success, sets cookies via the same `setAuthCookies()` helper `login/route.ts` already used (nothing new to extract — it was already shared). **On any failure — wrong code, expired code, already-consumed code, or a genuinely-verified phone with no linked account — responds with the exact same `INVALID_OR_EXPIRED_CODE`.** `proton_auth_plugin` deliberately collapses all of these into one identical empty result specifically to prevent phone-number enumeration; this route (and `LoginForm.tsx`'s error display) must preserve that ambiguity, not undo it by being more specific. Verified live, not assumed: wrong code, an expired code (DB-forced), and a correctly-verified-but-unregistered phone all produced the byte-identical `401 {"error":"INVALID_OR_EXPIRED_CODE"}`, and the UI showed the identical generic message for it.
- **Resend cooldown** — `LoginForm.tsx` runs a client-side 60s countdown matching `proton_identity`'s real server-side cooldown (see that service's README) purely for UX; the server remains the actual source of truth (`/api/otp/send`'s own `rate_limited` outcome is still handled if the two ever drift, e.g. after "Change number" resets the client-side timer to 0 for what might be a brand-new number).
- **proton_identity outage handling differs from send to verify, on purpose**: `/api/otp/send` failing surfaces `phoneLogin.errors.serviceUnavailable` with a one-click "Switch to email login" — verified live (stopped `proton_identity`, confirmed the phone tab degrades gracefully with no crash and the email tab keeps working unaffected). A `phone-login` failure (verify step) still just shows the generic invalid-code message — proton_auth_plugin's own `_verify_otp` already fails closed against a proton_identity outage (see that plugin's README), so from this route's perspective a wrong code and an outage are indistinguishable by design, not an oversight.
- **Post-login behavior, not forked per method**: `LoginForm.tsx`'s `completeLogin()` is the single shared tail-end (state update, `pendingPhone` flush, modal-close/redirect) both the email and phone paths call — added specifically so phone-login didn't grow a parallel, divergent copy of that logic.
- **Verified live, end-to-end, including the strongest available proof the token is real**: a full send→verify→login round trip through the actual UI against a real registered phone, then loaded the **checkout sub-app** with that session — Contact step correctly showed the signed-in account (email + "Sign out") exactly as it does for a password login, confirming Session 38's cookie-bridge customer-recognition works identically regardless of how the token was minted.
- i18n namespace `phoneLogin` (`en`/`ar`), reusing `auth.email` for the Email tab label and `phoneField` for the phone input itself rather than duplicating either.

## Account Deletion

`accountRequestDeletion`/`accountDelete` are self-service only (`AUTHENTICATED_USER`). **Load-bearing fact**: after `accountDelete`, the user row is hard-deleted but past orders **survive** with `user_id = NULL` while `order_order.user_email` and linked address PII (name/phone/street) are left **completely untouched** — Saleor does not anonymize historical order PII. This is disclosed explicitly in `accountDeletion.whatIsKeptBody` — do not soften that copy.

- GraphQL: `AccountRequestDeletion.graphql` + `AccountDelete.graphql` (additive). Actions: `requestAccountDeletion`, `confirmAccountDeletion` (`account/actions.ts`) — the latter checks for an access-token cookie itself before calling the mutation (handles cross-browser/signed-out email-link clicks) and clears both cookies directly on success rather than waiting for `logout()`.
- `DeleteAccountModal.tsx` — type-to-confirm literal English word `"DELETE"` (hardcoded `CONFIRM_WORD`, case-sensitive, always English even in Arabic UI), `status-danger` tokens throughout (not hardcoded `red-*`). Optional "reason for closing" `<select>` fires a fire-and-forget `POST /api/account-deletion-feedback` (hardcoded recipient `info@tawasiplus.com`, English-only ops email) alongside the real deletion request.
- `/delete-account/page.tsx` + `DeleteAccountConfirm.tsx` — 4 states (missing token / not authenticated / expired-invalid / success → auto-logout + redirect after 2s).
- "Download Your Data" card in SettingsSection — purely client-side, builds JSON from already-fetched `user.orders`/`user.addresses`, downloads via Blob + `<a download>`. No new GraphQL, no backend changes.

## Recently Viewed Products

`User.metadata` (public, self-writable, no staff permission needed) stores key `"recentlyViewed"` — JSON array of `{slug, viewedAt}`, capped 20, newest-first, deduped (repeat view moves entry to front). No atomic append (`updateMetadata` is full key-overwrite) — accepted last-write-wins race risk.

- GraphQL: `UserDetailsFragment` +`metadata`; `UpdateUserMetadata.graphql`; `ProductsBySlugs.graphql` (`products(filter:{slugs},...)`)
- `account/actions.ts`: `recordProductView(slug)` — fire-and-forget from a `useEffect` in `ProductInfo.tsx` (guarded by `isLoggedIn`), reads/writes metadata via the token cookie. `getRecentlyViewed()` — read-only counterpart.
- `account/page.tsx` resolves slugs → products via `ProductsBySlugsDocument`, then **re-maps through the original ordered slug list** (Saleor's `filter:{slugs}` gives no ordering guarantee) — this is also what makes a deleted/unpublished product silently disappear. `RecentlyViewedSection.tsx` reuses `ProductElement`.

## Trending Products — proton_analytics Integration

Wires the storefront to `proton_analytics` (separate internal microservice — see `saleor_platform/docker-compose.yml`). Write path records every visitor's product views; read path renders a homepage "Trending Now" section. No new dependencies.

- `ANALYTICS_SERVICE_URL` (server-side only, never `NEXT_PUBLIC_`) — proton_analytics has no auth.
- Write: `src/app/api/analytics/track-view/route.ts` — same-origin proxy, 2s timeout, always answers 202 (analytics outages never surface in the browser). Trigger: a second, independent `useEffect` in `ProductInfo.tsx` (ungated by `isLoggedIn`, unlike the adjacent `recordProductView` effect — trending counts every visitor). React StrictMode double-invokes effects in dev, so each dev page view registers as 2 — production does not, this is expected.
- Read: `src/graphql/ProductsByIds.graphql` (additive, root-level per this project's flat `src/graphql/` convention). `TrendingSection.tsx` fetches `/trending?limit=8` (`revalidate: 300`), resolves ids via Saleor, then **explicitly re-sorts back into analytics score order** via a `Map` (Saleor's `filter:{ids}` gives no ordering guarantee). Renders `null` on any failure or fewer than 4 resolved products. The Saleor call is wrapped in its own try/catch — Saleor rejects the **entire** `filter:{ids}` query if even one id is invalid, which would otherwise take the whole homepage down over a decorative section. **Do not remove this guard.**
- Mounted between FeaturedProductsSection and CategoriesSection, `<Suspense>`-wrapped.
