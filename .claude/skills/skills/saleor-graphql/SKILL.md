# GraphQL Conventions (Tawasi Plus Storefront)

## The additive-only rule

- `src/graphql/` — **only ADD new `.graphql` files here, never edit or delete existing ones.** If an existing query is missing a field you need, create a new query/fragment file rather than modifying the shared one — see the `ProductOriginAttribute` fragment (session 37) added alongside the untouched `ProductListPaginated.graphql`, and `ProductOriginDetails.graphql` fetched via a separate `Promise.all` call rather than editing `ProductDetails.graphql`.
- `src/gql/` — **generated output, never touch manually.** It's gitignored in some configurations (regenerated by a `prebuild` step) — don't hand-edit types here even temporarily.
- File placement: all 20+ query files live at `src/graphql/` root; only `fragments/` and `mutations/` are subdirectories. Don't invent a new `queries/` subdirectory to "organize" things — follow the existing flat layout for queries.

## Standard fetch pattern

```ts
// ✅ Correct
import { ProductDetailsDocument } from "@/gql/graphql";
const { data } = await executeGraphQL(ProductDetailsDocument, { variables });

// ❌ Never inline GraphQL strings via raw fetch
```

Exception: a couple of Route Handlers (e.g. `set-password/route.ts`, `confirm-account/route.ts`) deliberately use a raw inline mutation string + direct `fetch()` to `SALEOR_API_URL` instead of `executeGraphQL`/generated Documents — this mirrors an established convention for auth Route Handlers specifically. Match the convention of the file you're editing rather than "fixing" it to use `executeGraphQL` unprompted.

## Codegen workflow

```bash
# after adding/changing any .graphql file:
pnpm run generate
```

- The actual package.json script is **`generate`**, not `codegen` — don't guess the script name from memory of other projects.
- Always run it before using a newly-added Document, and confirm the generated field types (nullability especially) via `src/gql/graphql.ts` rather than assuming a field is non-null.

## Known Saleor GraphQL API behaviors worth knowing before you hit them as "bugs"

- **`products(filter: { ids })` throws on the entire query if even one ID is invalid** — a single junk ID from an external source (e.g. an analytics service) will throw `"Invalid ID specified."` past a Server Component's `<Suspense>` boundary straight to the error boundary, taking down whatever page called it. Wrap any Saleor call fed by external/untrusted IDs in its own try/catch, and treat that as required, not optional, for any similar batched-lookup feature.
- **`filter: { ids }` (and `filter: { slugs }`) give no ordering guarantee.** If display order matters (e.g. "show the top-scoring trending product first," or "preserve most-recently-viewed order"), build a `Map<id/slug, product>` from the result and re-map your own ordered source list through it — don't assume the API preserves the order you asked in.
- **`AttributeInput.values` accepts an array with OR semantics already** — "filter by any of these attribute values" needs zero schema changes; this is why the country-of-origin filter went from single-select to multi-select as a pure storefront parsing change (comma-separated `?country=` param → array), not an API change.
- **Introspect before assuming a mutation name or input shape.** `confirmAccount` (not `accountConfirm`) was the real mutation name for account activation, and `NameTranslationInput` turned out to have exactly one field (`name`) — both confirmed by checking `src/gql/graphql.ts` or live introspection rather than guessing from convention or memory of other Saleor projects.
- A field being permission-free at the field level doesn't mean there's a cross-user leak — e.g. `User.metadata` is writable/readable without a special permission on your **own** user object, but the top-level `user(id:)` query used to look up _other_ users is itself staff-gated. Check the surrounding query/mutation's auth requirements, not just the field.
